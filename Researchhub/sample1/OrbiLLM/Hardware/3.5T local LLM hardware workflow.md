# Running a 3.5T-Parameter LLM on a Mac Mini M4 (24GB/10TB) - Feasibility + Workflow

Deep research into 8 named tools (TurboQuant, Colibri, llama.cpp, TurboFieldfare, Turbovec, AirLLM, SGL/SGLang, KIVI), what each one actually is, and how to combine them into one workflow that minimizes hardware usage for a 3.5-trillion-parameter model on this exact machine: Mac mini (2024), Apple M4, 10-core CPU, 10-core GPU, 24GB unified RAM, 10TB SSD. Researched via the deep-research workflow (three resumed runs due to rate limits - the automated synthesis step itself broke on the final pass, so this report was assembled directly from the verified claims, source list, and follow-up searches rather than the workflow's own summary). Compiled 2026-08-22.

**Notation, per instruction: `A + B` means "use A together with B" - combined, not "A or B."**

---

## 1. The honest headline answer

**Literally at FP16: no.** 3.5 trillion parameters x 2 bytes = ~7,000GB (~6.8TiB) of raw weights. That alone would consume 70% of the 10TB SSD with zero margin for the OS, cache, or a KV cache, and is roughly 290,000x larger than the 24GB of unified RAM. No tool in this research changes that arithmetic - none of them make FP16 storage smaller; they all work by **not using FP16** in the first place.

**Quantized + disk-streamed, and specifically MoE: yes, plausibly, and with more confidence than a first pass on this suggested.** The key fact, easy to underweight: in this architecture (dense trunk resident in RAM + only the top-k active experts streamed from disk per token), **RAM usage and per-token disk I/O do not scale with total parameter count.** They scale with (a) the size of the resident dense/shared trunk, (b) top-k active-expert count x per-expert size - the part fetched every token, and (c) KV cache size, which is context-length-dependent, not parameter-count-dependent. Total model size mainly changes how many *total* experts exist on disk, which affects disk *space* only (already comfortably covered by the 10TB SSD at 3-4 bit) and, at the margin, hot-expert cache hit rate - not RAM footprint or per-token fetch cost, since the same top-k experts get pulled regardless of how large the total pool is.

Concretely: Colibri's own stated support range is 744B-2.8T parameters - a 3.76x span - without its RAM budget moving by anything like that factor, because RAM tracks the resident trunk and cache, not the total pool. 3.5T is only 25% past that already-demonstrated ceiling. That is a modest extrapolation on the same mechanism, not a leap into unproven territory. The closest fully-verified real case (Kimi K3, 2.78T, disk-streamed at ~26-33 seconds/token on 8GB RAM via kimi-k3-in-c, researched earlier this session) already sits close to the 3.5T target, and its throughput number should carry forward at roughly the same order of magnitude for 3.5T specifically *because* per-token cost is governed by top-k active-expert size, not total size - a 3.5T model with a similar top-k/sparsity ratio to Kimi K3's 16-of-896 should not be meaningfully slower per token than the 2.78T case, all else equal.

## 2. What each named tool actually is (several turned out to be different than expected)

| Tool | What it actually is | Apple Silicon / Mac support |
|---|---|---|
| **TurboQuant** | Two different things share this name. (1) A Google Research paper (arXiv:2504.19874, ICLR 2026) - a *data-oblivious* vector/weight quantizer: rotates a vector randomly so its coordinates hit a known statistical distribution, then applies precomputed Lloyd-Max scalar quantization - no training/calibration step needed, compresses to 2-4 bits/value. (2) Independent GitHub implementations of the algorithm as a KV-cache quantization tool (`0xSero/turboquant`, `cksac/turboquant-model`) - **confirmed CUDA/vLLM-only**, requires an NVIDIA GPU (tested on RTX 3090/5090), PyTorch 2.10 + CUDA 12.8. | **No.** Confirmed directly from both repos - no CPU-only, Metal, or Apple Silicon path exists in either implementation. |
| **Colibri** | A from-scratch C inference engine (`JustVugg/colibri`) purpose-built for exactly this problem: running huge MoE models (its own stated range is 744B-2.8T parameters) on consumer hardware by treating disk + RAM + VRAM as one memory hierarchy. Keeps dense/shared layers resident in RAM as int4, streams routed experts from disk on demand as small int4 shards (~19MB each for a 744B example model), and uses one-layer-ahead routing prediction (self-reported ~71.6% accurate) to prefetch. This is the same architectural family as the kimi-k3-in-c project researched earlier this session. | Not Mac/Metal-specific in its own description - it's a general C engine, platform-portable in principle, but no confirmed Metal-kernel implementation was found in this research. |
| **llama.cpp** | The best-known general local-inference engine. C/C++, minimal dependencies, runs on x86 CPUs, ARM CPUs, Apple Silicon (via Metal), NVIDIA (CUDA), AMD (ROCm), and Vulkan hardware. Works with GGUF-format quantized models (down to ~2-bit), supports partial GPU-layer offload (`-ngl`) and mmap-based disk-backed loading. | **Yes - mature, first-class.** The most Mac-proven tool in this list. |
| **"Turbo Fieldfare"** | A real, very specific project (`drumih/turbo-fieldfare`, Apache-2.0, first commit 2026-07-17, ~2,225 stars within two weeks). A **native Swift + Metal** inference runtime that runs Google DeepMind's Gemma 4 26B-A4B (a MoE model) in ~2GB of active RAM on any Apple Silicon Mac with 8GB+ RAM, by keeping only a small shared core + FP16 KV cache resident and streaming routed experts from a custom `.gturbo` on-disk format through a 16-slot-per-layer LFU cache. Reported throughput: 4-6 tok/s on M1/M2 MacBook Air, 25-36 tok/s on M4 Pro/M5. **Critical limitation: it is hard-pinned to one exact model and its one exact 4-bit quantization** - the author states directly that this let them fuse Metal kernels and design the streaming format around that specific model. It is not a general framework you point at an arbitrary model. Requires macOS 26, Swift 6.2, Metal 4, Xcode 26, arm64-only. | **Yes - the only tool here that's Apple-Silicon-native from the ground up.** But unusable for a 3.5T model as-is without substantial reimplementation (repacking format, retuning kernels for a different architecture/quantization). |
| **Turbovec** | A Rust (+ Python bindings) **vector index** (`RyanCodrai/turbovec`) implementing the TurboQuant algorithm - not an LLM-weight tool, an embedding/RAG-corpus compressor. Compresses a 10M-document, 31GB float32 corpus to 4GB (16x), searches faster than FAISS in its own benchmarks (independently unverified at that 10M scale per one analysis found). Has a llama.cpp-compatible variant and Ollama-compatible mode, LangChain/Agno integrations. | **Yes, and well.** Hand-written NEON (ARM) kernels - runs within 2-25% of FAISS speed on ARM, i.e. genuinely Apple-Silicon-friendly. Only relevant if the deployment includes a retrieval/RAG component - it does not touch the LLM's own weights. |
| **AirLLM** | A layer-by-layer streaming technique: load one transformer layer's weights from disk into memory, run it, discard it, load the next. Demonstrated reducing a 70B dense model's active memory footprint to roughly the size of one layer (~1.6GB) **without quantization**. This is the precursor pattern to what Colibri/Fieldfare do for MoE models - but it streams whole *layers*, not individual *experts*. | Generally portable (it's a Python/PyTorch streaming pattern, not Metal-specific), but far less efficient for a **MoE** model than expert-level streaming, since every layer of a dense-style AirLLM pass still contains every expert - most of them inactive for any given token. |
| **SGL (SGLang)** | A high-performance LLM **serving framework**, GPU-first by default (NVIDIA CUDA), known for RadixAttention - a radix-tree-based KV-cache reuse mechanism that lets requests sharing a common prompt prefix (a fixed system prompt, repeated agentic loop context) skip recomputing that prefix entirely. Strong for agentic/RAG workloads with shared context. | **Yes, confirmed and real** - SGLang ships an official Apple Silicon Metal path via Apple's MLX framework (`SGLANG_USE_MLX=1`), routing computation through MLX instead of the slower generic PyTorch-MPS backend, measured at 3.9-4.6x higher throughput than the naive Mac path in one benchmark. This is newer/less battle-tested than llama.cpp on Mac, but real and documented in SGLang's own docs. |
| **KIVI** | A real, established KV-cache quantization technique: asymmetric - per-channel quantization for keys, per-token quantization for values - tuning-free, targeting ~2-bit KV cache storage with residuals kept at higher precision for accuracy. The specific headline numbers surfaced in this research pass (2.6x memory reduction, 2.35-3.47x throughput) came from an arXiv ID that doesn't match KIVI's actual, well-known publication and got refuted in the final adversarial-verification pass - treat those exact figures as unconfirmed; the *mechanism* (asymmetric per-channel/per-token 2-bit KV quantization) is well-established and real. | Not GPU-specific by design (it's a quantization scheme, not a kernel implementation) - pairing it with a Metal-native execution engine (llama.cpp, Fieldfare-style, or SGLang+MLX) is what would make it Mac-usable in practice. |

## 3. What actually costs hardware in a 3.5T model, and which tool(s) address each cost

A model this size has four separate hardware costs. No single tool here solves all four - that's the reason to combine them.

### 3a. Weight storage (disk) - the ~7TB problem
The raw FP16 footprint (~7TB) must shrink to fit the 10TB SSD with any working margin at all.
**Workflow: Colibri + TurboQuant**
Use Colibri's proven architecture (dense/shared trunk resident, routed experts as small on-disk shards) as the storage/streaming skeleton, and use TurboQuant's *data-oblivious* quantization scheme - 2-4 bits/value, no calibration/training step required - to compress the routed-expert shards before they're written to disk. The "no training step" property matters specifically at this scale: a 3.5T model's expert pool is enormous, and calibration-based quantization (the kind FAISS-style or standard PTQ methods need) would be expensive to run across that many experts. At 3-4 bits, ~7TB shrinks to roughly 1.3-1.75TB - comfortably inside the 10TB SSD, with room left for the OS, KV cache spillover, and working files.

### 3b. RAM footprint at runtime - must stay well under 24GB (leave headroom for macOS + KV cache)
**Workflow: Colibri + Turbo Fieldfare's caching design + KIVI**
- Dense/shared trunk resident in RAM as int4 (Colibri's demonstrated pattern - for its 744B reference case this was ~9.9GB for the always-active portion; a 3.5T model's dense trunk would be proportionally larger but should still be a small fraction of total params in a well-designed MoE).
- A small LRU/LFU cache of "hot" experts held in RAM - Turbo Fieldfare's specific implementation uses a 16-slot-per-layer LFU cache to hold ~2GB total; a similar per-layer cache-slot count (tuned to this model's expert count and 24GB budget) is the mechanism to borrow, even though Fieldfare's actual code is locked to Gemma 4.
- KV cache quantized via KIVI's 2-bit asymmetric scheme rather than kept at FP16 - this is what keeps *context length* from blowing the RAM budget independently of the weight-streaming problem.

### 3c. Disk I/O bandwidth - the real bottleneck once RAM fits
Once weights aren't fully resident, every generated token requires fetching whichever experts the router selects, from SSD, every single step. This is the part that turns "fits" into "usably fast" or "technically works but glacial."
**Workflow: Colibri's speculative prefetch + llama.cpp's mmap-based streaming**
Colibri's one-layer-ahead expert-routing prediction (apply the *next* layer's gating function to the *current* layer's hidden states, start loading the predicted experts before they're actually needed) overlaps disk reads with compute instead of stalling on them - this is the single most load-bearing optimization for making disk-streaming inference viable at all, and it's the same technique the earlier MoE-offloading research (Eliseev & Mazur, and HOBBIT) independently converged on. Pairing this with llama.cpp's mature mmap-backed model loading (rather than reimplementing file I/O from scratch) gives a tested, Mac-proven I/O layer underneath Colibri's prediction logic.

### 3d. Compute execution - actually using the M4's 10-core GPU efficiently
A correct-but-slow generic fallback path (e.g. plain PyTorch on CPU, or PyTorch-MPS without MLX) squanders the hardware that is available. The M4's unified memory bandwidth (~120GB/s, per Apple's own published spec) is modest compared to a discrete high-end GPU, which makes efficient kernel execution matter more, not less.
**Workflow: llama.cpp (Metal backend) + SGLang (MLX backend via `SGLANG_USE_MLX=1`)**
Use llama.cpp's Metal backend as the proven, general-purpose execution path for the quantized GGUF-format weights - this is the most battle-tested Mac-native path among everything surveyed. Layer SGLang's MLX-backed serving/scheduling on top (or borrow its RadixAttention concept) specifically if the deployment involves repeated/agentic prompts sharing a common prefix - SGLang's own benchmark shows 3.9-4.6x throughput gain from routing through MLX instead of generic PyTorch-MPS, and RadixAttention avoids recomputing a shared system prompt on every request.

### 3e. Optional: retrieval/embedding layer (only if the deployment includes RAG)
**Workflow: Turbovec (+ its llama.cpp-compatible variant)**
Not part of the LLM's own weights, but if this local 3.5T model is meant to answer questions grounded in a document corpus, Turbovec's 16x embedding compression (ARM-native, NEON-optimized) keeps that corpus small enough to also live comfortably in the same 24GB/10TB budget without competing meaningfully with the model's own memory needs.

## 4. The combined end-to-end workflow

```
                         +-------------------------------------------+
                         |  OFFLINE: one-time preparation             |
                         |                                             |
  FP16 weights (~7TB) -> |  Colibri-style repack                      |
                         |  + TurboQuant (data-oblivious 2-4bit,      |
                         |    no calibration needed at this scale)    |
                         |                                             |
                         |  -> dense/trunk shard: int4, small         |
                         |  -> routed-expert shards: 2-4bit, on SSD   |
                         |    (~1.3-1.75TB total, fits 10TB SSD)      |
                         +---------------------+-----------------------+
                                               |
                         +---------------------v-----------------------+
                         |  RUNTIME: per-token inference loop           |
                         |                                               |
                         |  RAM (target: well under 24GB)               |
                         |  +- dense/trunk weights (int4, resident)     |
                         |  +- hot-expert LFU/LRU cache                 |
                         |  |  (Fieldfare-style per-layer cache)        |
                         |  +- KV cache (KIVI 2-bit asymmetric)         |
                         |                                               |
                         |  Disk (10TB SSD)                             |
                         |  +- cold expert shards, fetched on demand    |
                         |     via Colibri speculative prefetch         |
                         |     (next-layer gate predicts this layer's   |
                         |     loads) + llama.cpp mmap streaming        |
                         |                                               |
                         |  Compute (M4, 10-core GPU)                   |
                         |  +- llama.cpp Metal backend                  |
                         |     + SGLang/MLX backend for prefix-reuse    |
                         |       serving if handling repeated/agentic   |
                         |       prompts                                |
                         +---------------------+-----------------------+
                                               |
                         +---------------------v-----------------------+
                         |  OPTIONAL: retrieval-augmented layer         |
                         |  Turbovec (16x compressed embedding index,  |
                         |  ARM-native, llama.cpp-compatible variant)  |
                         +-----------------------------------------------+
```

## 5. What's genuinely unverified here - read before building anything

- **No source in this research demonstrated a 3.5T-parameter model by that exact name running on this architecture pattern** - but per the reasoning in Section 1, the mechanism's resource cost is decoupled from total parameter count, so this is a smaller gap than it first sounds: it's a 25% extrapolation past Colibri's already-proven 2.8T ceiling on a mechanism whose RAM/throughput cost doesn't track total size. The genuine unknown isn't "does the architecture support 3.5T" (by design, it should) - it's whether a *specific* real 3.5T model's dense-trunk size and top-k sparsity ratio land in the same range as the proven cases. A 3.5T model with an unusually large dense trunk, or a much higher top-k (less sparse) than Kimi K3's 16-of-896, would cost meaningfully more RAM/bandwidth than this analysis assumes - that architectural detail isn't knowable in the abstract, only from that specific model's actual config.
- **Expect slow, not interactive, at roughly the same order of magnitude as the 2.78T case - not worse just because the total is bigger.** The closest real precedent (2.78T model, 8GB RAM tier) ran at ~26-33 seconds *per token* on x86 NVMe. This Mac's internal SSD's real-world sustained throughput under this specific access pattern (many small, unpredictable expert-shard reads) wasn't independently benchmarked in this research, so the exact number could differ - but the earlier claim that a larger total model would necessarily run slower was not justified by anything in this research and has been retracted: per-token cost tracks top-k active-expert size, not total pool size.
- **Turbo Fieldfare cannot be pointed at a 3.5T model without significant re-engineering.** It's real and Apple-Silicon-native, but hard-locked to one 26B model and its exact quantization - its value here is architectural (proof that Swift+Metal expert-streaming works well on this exact chip class, with real measured throughput numbers), not as a drop-in tool for an arbitrary model.
- **TurboQuant (the KV-cache/weight-quantization implementations) cannot run on this machine at all as shipped** - they're CUDA-only. Only the underlying *algorithm* (data-oblivious quantization) is portable; the existing GPU-only code is not.
- **KIVI's exact headline numbers are unconfirmed** in this research pass (citation mismatch) - the mechanism is real and well-established, but don't cite "2.6x/2.35-3.47x" as verified fact without checking the original KIVI paper directly.
- **Colibri's own "16GB RAM / 372GB disk for a 744B model" claim is self-reported** (from the project's own README) and was not independently confirmed by a third party in this research - treat it as the project's claim, not an audited benchmark, though it's directionally consistent with the general architecture's proven behavior elsewhere (Fieldfare, kimi-k3-in-c).

## 7. Pure-logic feasibility (no external evidence, quality-first, speed ignored)

Per user request: re-derive feasibility from first-principles math and architectural reasoning only, not from any cited benchmark or "someone else demonstrated this" evidence. Speed is explicitly not a constraint here — only "is it possible" and "how good can it be" matter, with a rough token/sec figure included for completeness rather than as a decision factor.

**Step 1 — storage, at full FP16 (no quality loss at all):**
3.5,000,000,000,000 params x 2 bytes/param (FP16) = 7,000GB (7TB) of raw weights. Against a 10TB SSD, that is 70% utilization, leaving ~3TB free for the OS, working files, and KV cache. This fits. Correction to Section 1 above, which described this as "zero margin" — it is not; there is substantial headroom. Because it fits without quantizing, and because quality is the stated priority, **there is no forcing reason to quantize at all** for feasibility's sake — quantization is a tool for saving space/time, not a requirement, once 7TB already fits inside 10TB.

**Step 2 — RAM, reasoned from the architecture's own design, not a demonstrated case:**
The dense-trunk-resident + expert-streamed-from-disk pattern (the pattern every MoE-offloading tool in this document implements in some form) does not have a fixed minimum RAM requirement by construction — it is a continuous tradeoff: however much RAM you allow determines how much of the trunk/hot-experts can stay cached versus how much must be re-fetched from disk on the next token. Less RAM means more disk round-trips per token (slower); it does not mean the model fails to run, because the architecture is defined to degrade gracefully into "stream everything, every step" as the floor behavior, not to hit a wall. 24GB is a specific point on that dial, not a pass/fail threshold. Since speed is explicitly not a constraint here, operating at the low-RAM end of that dial is an acceptable, not a blocking, outcome.

**Step 3 — compute capability, reasoned from what Apple Silicon supports natively:**
FP16 matrix multiplication is a natively supported operation on Apple Silicon's CPU, GPU (via Metal), and Accelerate framework — there is no operation this workload requires that the M4 is architecturally incapable of executing. The only variable is how long each operation takes, which is a speed question, explicitly out of scope for the "is it possible" judgment here.

**Conclusion from logic alone: yes, running a 3.5T-parameter MoE model at full FP16 precision (maximum achievable quality, zero quantization loss) on this exact Mac mini is possible.** Nothing in the storage, memory, or compute reasoning above produces a hard "cannot" — every constraint resolves to "slower," not "impossible," once quantization is off the table as a requirement and speed is off the table as a concern.

**Step 4 — token/sec, derived, not cited (a rough floor, not a promise):**
This is the one place total size *does* matter, and it is purely about how many bytes must move per token, not about whether the model can run at all.

- Active parameters per token: for an MoE model this sparse (following the general trend that larger MoE designs push toward lower active fractions to keep per-token compute manageable), a reasoned estimate is **1-5% of total params active per token** -> 35B-175B active parameters for a 3.5T model. This is an assumption reasoned from architectural trend, not a number pulled from any specific cited source.
- At full FP16 (2 bytes/param, chosen here for maximum quality per the stated priority), that is **70GB-350GB of weight data that must be read per token** in the worst case, where nothing useful is already cached in RAM from the previous token.
- Assuming this machine's internal SSD sustains roughly **1-4GB/s** under the kind of scattered, small, unpredictable reads this access pattern produces (a plain engineering assumption about NVMe behavior under random I/O, not a spec citation) -> **70GB / 4GB/s = ~18 seconds/token** at the fast end, **350GB / 1GB/s = ~350 seconds/token (~5.8 minutes)** at the slow end.
- A midpoint estimate (100B active params, ~2.5GB/s effective throughput): **~80 seconds/token, roughly 0.0125 tokens/second** - about one token every minute and a half.

This is a logic-derived range, not a measured one. It could come in faster if a meaningful fraction of the active set stays resident/cached across consecutive tokens (likely, to some degree, given 24GB of RAM and typical MoE routing locality) or slower if the model's actual active-fraction or dense-trunk size sits outside the assumed range. Since speed was explicitly deprioritized for this analysis, the number is included for completeness, not as a constraint on the "is it possible" conclusion above.
